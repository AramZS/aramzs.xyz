<p>One of the interesting trends that is happening across all industries is the rise of AI and AI-integrated tooling. I think most of us have experimented with running local LLMs through projects like Ollama and OpenWebUI. But a lot of these feel more like a chatbot that things that are super helpful in the lab, even though they are powerful. However, I have recently spent some time testing OpenCode connected to Ollama with local coding models running directly from inside my <a data-wpil-monitor-id="4852" href="https://www.virtualizationhowto.com/home-lab/">home lab</a>. After going through the setup and experimenting with them, this to me is where things get more exiting with AI coding agents. And the cool thing is, you don’t need cloud APIs, subscriptions, or any of your code leaving your network. Let’s walk through using OpenCode in your home lab and how to get this setup.</p>

<h2 data-vht-link-ready="1">What is OpenCode?</h2>
<p>You have probably started to hear about <a href="https://github.com/anomalyco/opencode">OpenCode</a> a lot about it lately. It is similar to what tools like Cursor, Claude Code, or Codex terminal interfaces look like. But the important thing is that it is something you can self-host and run locally and tie into your existing AI self-hosted resources like <a href="https://ollama.com/download">Ollama</a>. With AI coding agents, these can interact with your local filesystem and repos directly from the terminal.</p>

<p>So, instead of running like a basic chatbot, OpenCode can do the following:</p>
<ul> <li>Read files</li> <li>Go through project folders</li> <li>Analyze repos</li> <li>Suggest edits</li> <li>Search through code</li> <li>Help explain infrastructure</li> <li>Interact with tools</li> <li>Work with terminal tasks and workflows</li> </ul>
<p>This is what starts moving the experience from “chatbot” into “agent.” The really interesting part for home lab users is that OpenCode can connect to local models running through Ollama which I think is super cool and the most desirable if you want to experiment with self-hosting your own AI environment.</p>
<p>It means you can run your coding agent fully local without depending entirely on cloud providers. For me, this became interesting because I spend a huge amount of time working with things like Docker Compose, Kubernetes manifests, Bash scripts, Terraform, Ansible, Powershell, and the list goes on. These are just the types of things that an AI coding agent that you are hosting locally is really good at.</p>
<h2 data-vht-link-ready="1">Why I wanted to try this locally</h2>
<p>I have experimented with local LLMs before. Like many people, I initially tested Ollama together with OpenWebUI. While it was fun to ask questions and test prompts, I honestly did not find most local models particularly useful compared to cloud-hosted AI systems. You are locked into a really chatbot style workflow and I found the performance with pointing VS Code or another tool to use Ollama as a coding agent itself to be pretty terrible.</p>
<p>Coding especially felt weak pointed to Ollama directly. However, that is why OpenCode caught my attention. It combines the idea of local models, agentic tooling, filesystem access, repo awareness, and terminal workflows. So this feels much more practical from a coding and “usefulness” perspective than a self-hosted chat platform.</p>
<p>Also, if you value privacy and I know most of us do, when working with infrastructure code, internal configurations, or <a data-wpil-monitor-id="4858" href="https://www.virtualizationhowto.com/2026/01/best-automation-projects-you-can-build-for-proxmox-in-a-home-lab-in-2026/">automation projects</a>, there is definitely something to be said for keeping everything inside your own environment. For home lab users especially, this creates an interesting middle ground between experimentation and something that really is practical unlike what I have found before OpenCode.</p>

<h2 data-vht-link-ready="1">Connecting OpenCode to Ollama</h2>
<p>This was the part that I wasn’t sure about until exploring the options and ways of connecting OpenCode to various providers. Ironically, there isn’t an option in the OpenCode text GUI for Ollama, only Ollama Cloud. You will only see the option for <a data-wpil-monitor-id="4854" href="https://www.virtualizationhowto.com/2024/06/local-llm-model-in-private-ai-server-in-wsl/">Ollama Local</a> if you create the <strong>opencode.json</strong> file down below.</p>
<figure><a href="https://www.virtualizationhowto.com/wp-content/smush-webp/2026/05/ollama-local-and-ollama-cloud-1.png.webp"><img alt="Ollama local and ollama cloud" data-lazy-sizes="(max-width: 569px) 100vw, 569px" data-lazy-src="https://www.virtualizationhowto.com/wp-content/smush-webp/2026/05/ollama-local-and-ollama-cloud-1.png.webp" data-lazy-srcset="https://www.virtualizationhowto.com/wp-content/smush-webp/2026/05/ollama-local-and-ollama-cloud-1.png.webp 569w, https://www.virtualizationhowto.com/wp-content/smush-webp/2026/05/ollama-local-and-ollama-cloud-1-265x125.png.webp 265w, https://www.virtualizationhowto.com/wp-content/smush-webp/2026/05/ollama-local-and-ollama-cloud-1-150x71.png.webp 150w" src="https://www.virtualizationhowto.com/wp-content/smush-webp/2026/05/ollama-local-and-ollama-cloud-1.png.webp"/></a><figcaption>Ollama local and ollama cloud</figcaption></figure>
<p>The solution to getting OpenCode pointed to your local Ollama instance is to create a local OpenCode configuration file, opencode.json as mentioned.</p>
<p>On Windows, I created this file here:</p>
<pre data-copy-ready="1" data-slot-rendered-content="true"><code>C:\Users\localadmin\.config\opencode\opencode.json</code></pre>
<p>In Linux, it is located here:</p>
<pre data-copy-ready="1"><code>~/.config/opencode/opencode.json</code></pre>
<p>Inside the file, I configured OpenCode to use Ollama’s OpenAI-compatible API endpoint with the baseURL address. Also, you tell it <strong>which models</strong> to use. Here I started out with <strong>carstenuhlig/omnicoder-9b:latest</strong> which works well on my RTX 5080 with 16 GB of RAM.</p>
<pre data-copy-ready="1" data-slot-rendered-content="true"><code>{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Ollama Local",
      "options": {
        "baseURL": "<strong>http://127.0.0.1:11434/v1</strong>"
      },
      "models": {
        "<strong>carstenuhlig/omnicoder-9b:latest</strong>": {
          "name": "<strong>Omnicoder 9b</strong>"
        }
      }
    }
  }
}</code></pre>
<p>One important detail here is the <code><strong>/v1</strong></code> endpoint. Without <code>/v1</code>, the <a data-wpil-monitor-id="4862" href="https://www.virtualizationhowto.com/2011/09/linux-network-connection-not-working-virtual-machine-esxi/">connection generally won’t work</a> correctly because OpenCode expects the OpenAI-compatible API interface from Ollama. After restarting OpenCode, the local models became available.</p>

<h2 data-vht-link-ready="1">Choosing the right local model matters a lot</h2>
<p>This was a learning experiment for me since I hadn’t experimented as much with coding agent configurations in a self-hosted way. Not all coding models are equal when it comes to AI coding agents. For instance, I had DeepCoder 14B downloaded, but saw this when trying to use it with the OpenCode platform below. It told me the model <strong>did not support tools</strong> which is must support for the AI agents that OpenCode uses.</p>

<p>Agentic coding systems depend heavily on tool usage. The model needs to support things like:</p>
<ul> <li>File inspection</li> <li>Filesystem traversal</li> <li>Structured tool calls</li> <li>Repository search</li> <li>Terminal actions</li> <li>Context-aware operations</li> </ul>
<p>Without tool support, the experience isn’t very good and will descend into the experience of simply using a standard chatbot. The model can answer coding questions, but it cannot truly operate as an agent. That is where LLMs like Omnicoder 9b felt better.</p>
<p>I switched to <strong>carstenuhlig/omnicoder-9b:latest</strong> and the experience improved dramatically.</p>
<pre data-copy-ready="1" data-slot-rendered-content="true"><code>ollama pull carstenuhlig/omnicoder-9b:latest</code></pre>
<p>Now, OpenCode could properly read project folders, analyze repositories, explain files, traverse directories, and interact with local projects. This completely changes the experience.</p>
<h2 data-vht-link-ready="1">Launching and using OpenCode for your projects</h2>
<p>The way to launch Opencode so that it has understanding and context with your folder or project is that you change to your folder containing the files you want to work with and then you launch opencode from there.</p>
<p>For example:</p>
<pre data-copy-ready="1"><code>cd C:\repos\terraform-proxmox<br/>opencode</code></pre>
<p>Once launched inside the project root, the agent can start understanding structure of the repository and files you want to work with. This is especially useful for infrastructure-as-code repositories where the context spans multiple files.</p>

<h2 data-vht-link-ready="1">Hardware you will need and model size</h2>
<p>One thing worth discussing when talking about OpenCode or any other self-hosted AI solution that you want to run in your home lab. You will need to have a decent video card. While you “can” <a data-wpil-monitor-id="4860" href="https://www.virtualizationhowto.com/2023/08/intel-n100-4-cores-can-this-little-cpu-run-vms/">run models entirely on a modern CPU</a>, the performance is mediocre to poor at best in my honest opinion.</p>
<p>Smaller models like 7B variants will run on many systems, but once you move into stronger coding models like 14B or 32B variants, the hardware demands will increase and you want to have the right hardware for the job.</p>
<p>For my testing, <strong>the 7b and 14b models</strong> felt like the sweet spot between:</p>
<ul data-slot-rendered-content="true"> <li>Performance</li> <li>Quality</li> <li>Resource usage</li> <li>Responsiveness</li> </ul>
<p>The <strong>32B models</strong> can absolutely perform better, but they also require a ALOT more <a data-wpil-monitor-id="4856" href="https://www.virtualizationhowto.com/2025/11/increase-usable-ram-in-your-home-lab-without-buying-more-memory/">RAM or GPU memory</a>. For many home lab users, a <strong>14B model</strong> is probably the best middle of the road starting point for consumer grade video cards.</p>

<h2 data-vht-link-ready="1">Current limitations to note</h2>
<p>Even though I was pretty impressed with my little local AI coding agent setup with OpenCode, <strong>cloud models are still noticeably better</strong>. Large hosted models still will outperform your local models in many areas like deep reasoning, large repo awareness, multi-step planning, long context handling, debugging, etc.</p>
<p>So, like me, you will probably find they perform the best on focused projects instead of massive repos and large code bases. But, I think for most in the home lab, this is acceptable and definitely in the realm of what many are doing with infrastructure as code projects in their home labs.</p>
<p>But with those things said, I do think the gap is narrowing much faster between what we can do locally and what you get with a cloud-based model.</p>
<h2 data-vht-link-ready="1">Why I think this is a shift in the way we operate home labs</h2>
<p>These solutions like OpenCode are extremely important I think for home labs over the next couple of years. I think for a long time, we were super focused on things like virtualization, storage, networking, Kubernetes, self-hosting, etc.</p>
<p>And while those things are still important and we will continue to build around those, I think we are moving into an era where self-hosted AI that is actually worth self-hosting is possible and is part of the group of projects that are now worthwhile in a lab. People are starting to build local inference servers, GPU nodes, AI development environments, agentic workflows, and more interesting projects around AI.</p>
