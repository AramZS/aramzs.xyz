<p>A coding agent's session holds what nothing else records: the commands it ran, what they printed, what it tried and abandoned, and why. Diderot is an open-source server you run. It indexes those sessions alongside your team's chat, issues and docs, searches all of it over several rounds, and answers with citations.</p>

<h2>How a session becomes searchable</h2>
<p>See <a href="https://diderot.dev/docs/session-ingest/">Agent-session ingest</a>.</p>
<p>A session can run for hours. Diderot summarizes each chunk and the whole session, embeds both summaries, and keeps the transcript. A question finds the right ten minutes and gets back the command as it was typed. Sessions arrive from the <code>diderot</code> client on each person's machine, or from an uploader of your own.</p>

<h2>Memory an agent searches, instead of a file it loads</h2>
<p>A memory file such as <code>CLAUDE.md</code> or <code>AGENTS.md</code> is loaded into the context window at the start of every session, whether the task needs it or not. Someone has to keep it short enough to fit, and it lives in one repository or on one machine.</p>
<p>Diderot keeps agent sessions alongside your team's chat, issues and docs in Postgres and Qdrant. Corpus text enters an agent's context window only when the agent calls a tool: <code>retrieve</code> for the passages that match a question, <code>expand</code> for up to 64 KiB of the transcript, thread, issue or page behind a hit. A new session can find what an earlier one did, yours or a colleague's, within what the caller may read.</p>

<h2>Several rounds of retrieval, not one search</h2>
<p>Diderot's first move is one search across every source. Each source is ranked on its own and the best few results of each come back together, so a runbook or an issue is not buried under a busy chat. Then it works in rounds: <code>retrieve</code> in one source for more, <code>list</code> for everything matching a filter, <code>expand</code> for the full thread, page, issue or stretch of a session around a hit. It answers when every claim rests on something it has read, and cites it.</p>
<p>If you connect them, it can also search your code, search the web, call the read-only tools of MCP servers you connect in the admin UI, and hand an investigation of your telemetry to a separate investigator. Slack, Discord, the shell, MCP and the HTTP API all run this same loop.</p>
<h2>One place to ask</h2>
<p>See <a href="https://diderot.dev/docs/design/#sources">Design: sources</a>.</p>
<p>The answer to a real question is usually spread across chat, the tracker, the wiki and agent sessions. Instead of asking a Slack assistant, then a Linear one, then grepping transcripts, you ask one corpus that holds all of it.</p>
<dl><dt>Coding-agent sessions</dt><dd>The transcripts you send it, from Claude Code, Codex and other harnesses.</dd><dt>Slack</dt><dd>Messages and threads in the channels the bot is in, with their images and PDF, DOCX and XLSX attachments.</dd><dt>Discord</dt><dd>The channels you choose, with their threads and forum posts.</dd><dt>Linear</dt><dd>Issues and their comments.</dd><dt>Notion</dt><dd>The page trees you choose.</dd><dt>Zendesk</dt><dd>Tickets, their comments and Help Center articles.</dd><dt>A folder of Markdown files</dt><dd>A docs repository, runbooks, a handbook.</dd></dl>
<p><b>Images too.</b> AI vision reads what is inside your images, so screenshots, charts and scanned documents are searchable by their content.</p>
<h2>Your models, your prompts</h2>
<p>See <a href="https://diderot.dev/docs/design/#inference-providers">Inference providers</a> and <a href="https://diderot.dev/docs/prompts/">Prompts</a>.</p>
<h3>Every job takes the model you give it</h3>
<p>Diderot ships with no model and starts with none configured. In the admin UI you add a provider: OpenAI, Anthropic, or anything that speaks OpenAI's API, such as a gateway or a local Ollama or vLLM. Diderot lists the provider's models, and you choose one for each job: answering, embedding, summarizing sessions, describing images. Each is tested before it is saved, and there is no configuration file for any of it. One install can mix a hosted model for answers with a local one for embeddings.</p>
<h3>Every prompt is yours to change</h3>
<p>The instructions Diderot sends to a model are named prompts in one catalog: how Ask researches, how it writes for Slack, how it summarizes a session, describes an image and investigates an alert. You edit them in the browser. Changes collect in a draft, shown line by line against the live text, and go live together as one version with a note. Any earlier version can be made live again, and an optional note about your organization tells Ask where your team keeps things.</p>

<h2>For coding agents</h2>
<p>See <a href="https://diderot.dev/docs/cli/">The <code>diderot</code> command</a> and <a href="https://diderot.dev/docs/auth/#mcp-endpoint">MCP endpoint</a>.</p>
<p>To connect your coding agents, install the <code>diderot</code> client on your own machine and give it a server's URL. It signs in, registers Diderot's MCP server with the coding agents you name, and installs the skill that teaches them when and how to use it:</p>
<pre><code data-lang="sh">brew install bluesky-social/tap/diderot
diderot setup https://diderot.example.com \
  --harness claude-code,codex
diderot doctor
diderot ask "What did we decide about the billing migration?"</code></pre>
<dl><dt><code>setup</code></dt><dd>Knows Claude Code, Codex, Cursor, OpenCode and Pi. It works out how to sign in from the URL: an API token, or OAuth in your browser when the server or a gateway in front of it publishes MCP authorization metadata, as a Diderot server in <code>oidc</code> mode does. It changes only the <code>diderot</code> entry in each agent's configuration, and running it again is safe.</dd><dt><code>doctor</code></dt><dd>Checks the connection, the sign-in and everything <code>setup</code> configured. It changes nothing.</dd><dt><code>ask</code></dt><dd>Asks from the shell and prints the answer with its citations. <code>--session</code> asks a follow-up in the same conversation.</dd><dt><code>sessions</code></dt><dd>On a terminal, after sign-in, <code>setup</code> checks that the server takes sessions from your account, lists the Claude Code and Codex session directories it finds on your machine, and offers to ship them. If the server does not, it asks nothing and installs nothing. Yes installs a background service under your own account, a launchd agent on macOS or a systemd user unit on Linux. It converts each session on your machine and sends the whole transcript to that server, unredacted, with images left out. <code>diderot sessions install</code> does the same later, and <code>uninstall</code> removes the service. Sessions are stored but not searchable until an administrator has chosen a model for both session-summary jobs on the server's Models page.</dd></dl>
<p>Without Homebrew, <a href="https://diderot.dev/docs/cli/#install">download the release archive</a> for Linux or macOS and check it against the release's <code>checksums.txt</code>, or build it with <code>go install github.com/bluesky-social/diderot@latest</code>. The download holds only the client commands <code>setup</code>, <code>doctor</code>, <code>ask</code> and <code>sessions</code>; the server's commands are in the container image. Off a terminal every command prints one JSON object, so scripts and agents can drive it.</p>
<h3>The MCP server underneath</h3>
<p>Everything <code>setup</code>, <code>doctor</code> and <code>ask</code> do goes through the server's MCP endpoint, <code>/mcp</code>, which every install serves over streamable HTTP with the same bearer token the HTTP API takes. Any other MCP client can point at it directly. It has the tools Ask itself uses, <code>retrieve</code>, <code>list</code> and <code>expand</code>, plus <code>attachment</code>, which returns an image or a document's extracted text, and <code>ask</code>, which returns a full cited answer. <code>ask</code> runs as an MCP task, so it needs a client that implements the MCP Tasks extension; the other four work in any client. Each call sees what the caller's identity may see.</p>
<p>Without MCP, the same token works on the plain HTTP API: <code>POST /v1/ask</code>, <code>/v1/retrieve</code>, <code>/v1/list</code> and <code>/v1/expand-chunk</code>.</p>

<h2>Try it on one machine</h2>
<p>See the full <a href="https://diderot.dev/docs/quickstart/">Quickstart</a>, including troubleshooting.</p>
<p>The quickstart runs Postgres, Qdrant, a local embedding model and the server with Docker Compose. You need Docker Engine 25 or later with Compose v2.24.4 or later, about 4 GB of memory for Docker, about 9 GB of free disk, and an API key for OpenAI, Anthropic or another provider. With no other source, it can index Diderot's own documentation, so there is something to ask about.</p>
<ol><li><p>Start it. It needs no settings file and no key yet. The first run builds the server image and downloads the embedding model, which takes a few minutes.</p><pre><code data-lang="sh">git clone https://github.com/bluesky-social/diderot.git
cd diderot
docker compose -f compose.quickstart.yaml up -d --wait</code></pre></li><li><p>Open <code>http://localhost:9091/admin</code> and sign in as <code>admin</code> / <code>admin</code>. On <b>Models</b>, add your provider with its key and the bundled local embedder; Diderot lists their models, and you choose one for embeddings and one for each job.</p></li><li><p>Finish the setup checklist: name your organization, turn on a source (a folder of Markdown files needs no account) and go live. One step replaces the <code>admin</code> account.</p></li><li><p>Ask. Connectors sync in the background, and each item is searchable as soon as the embedder has processed it. The local embedder takes a few minutes to index Diderot's docs. Ask answers <code>503</code> for a moment after the server starts: retry.</p><pre><code data-lang="sh">export DIDEROT_TOKEN="$(docker compose -f compose.quickstart.yaml run --rm -T init cat /keys/api-token)"
curl -sS http://localhost:9091/v1/ask \
  -H "Authorization: Bearer $DIDEROT_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"question": "How do I add a source to Diderot?"}'</code></pre></li><li><p>Connect your coding agents. Install the <code>diderot</code> client (<a href="https://diderot.dev/docs/cli/#install">other ways to install it</a>); in the same shell, <code>setup</code> registers the server with them and installs the agent skill:</p><pre><code data-lang="sh">brew install bluesky-social/tap/diderot
printf %s "$DIDEROT_TOKEN" | diderot setup http://localhost:9091 \
  --harness claude-code --token-stdin
diderot doctor
diderot ask "How do I add a source to Diderot?"</code></pre><p>To ship your own Claude Code and Codex sessions too, turn on session push and choose a model for both session-summary jobs on <b>Models</b>, as the Quickstart's <a href="https://diderot.dev/docs/quickstart/#agent-sessions">Agent sessions</a> describes, then run <code>diderot sessions install</code>.</p><p>Any other MCP client points at <code>http://localhost:9091/mcp</code> with the token as a bearer credential.</p></li></ol>
<p>The quickstart listens on <code>127.0.0.1</code> only. Ask sends each question, and the corpus text it reads to answer it, to the model provider you added.</p>

<ol><li><b>Connectors</b> read each source, by live events, periodic sync, HTTP push or a folder scan, depending on the source.</li><li><b>The events sink</b> writes one row per message, page, issue or session, idempotent on source and external ID. It skips content that has not changed, so nothing is embedded twice.</li><li><b>Postgres</b> is the source of truth: events, chunks, settings, prompts and every Ask conversation.</li><li><b>The embedder</b> cuts each event into chunks, embeds them through your embedding model, and marks a chunk embedded only after its vector is written. A vision model describes each image and transcribes its text; the embedder embeds that description, not the pixels.</li><li><b>Qdrant</b> holds the vectors, with each chunk's permission scope in its payload.</li><li><b>Surfaces</b>: a mention or direct message in Slack or Discord, the MCP server at <code>/mcp</code>, and <code>POST /v1/ask</code>. All run the same loop.</li><li><b>Ask</b> calls <code>retrieve</code>, <code>list</code> and <code>expand</code>, plus any optional tools you enabled, until it can answer. <code>retrieve</code> searches Qdrant; <code>list</code>, <code>expand</code> and the text of every hit come from Postgres, which checks each event's scope a second time.</li><li><b>Model providers</b> are the endpoints you add in the admin UI, called by the embedder and by Ask. Each request goes to the provider its model names, with that provider's key.</li></ol>
<p>Retrieval is vector-only: Diderot embeds the question and Qdrant returns the nearest chunks the caller may see. A search across several sources ranks each source on its own and returns the best few of each. There is no reranker and no keyword index. When a question contains an exact handle (a Slack permalink, a Linear issue key, a session ID), Diderot reads that record directly instead of searching.</p>
<p>A source of your own is one Go package and one registration line.</p>
<h2>Running it for a team</h2>
<p>See <a href="https://diderot.dev/docs/production/">Running in production</a>, with a complete Kubernetes example, and the <a href="https://diderot.dev/docs/configuration/">configuration reference</a>.</p>
<dl><dt>The server</dt><dd>One image runs the HTTP API, the browser UI, the MCP endpoint and the background workers. It is distroless, runs as a non-root user, and comes for <code>linux/amd64</code> and <code>linux/arm64</code>. Each release is published at <code>ghcr.io/bluesky-social/diderot</code>; to run a change of your own, build it with the repository's <code>Dockerfile</code>.</dd><dt>Postgres 14 or later</dt><dd>Holds every event, setting, sealed secret and conversation. The server applies its own migrations when it starts. Connect directly or through a session-mode pooler.</dd><dt>Qdrant</dt><dd>Holds the vectors, over gRPC, with optional TLS and an API key. It needs no backup: Postgres can rebuild it, at the cost of embedding the whole corpus again, and searches find less until that finishes.</dd><dt>Model providers</dt><dd>At least an embedding model and a model for Ask, added on the Models page once the server is up. Each request goes to the provider its model names, with that provider's key and no other.</dd><dt>Object storage, optionally</dt><dd>An S3-compatible bucket, if you want image captions and PDF, DOCX and XLSX extraction. Without one, attachments are not indexed.</dd><dt>An identity provider, or not</dt><dd>OIDC bearer tokens from your IdP, static tokens, or a loopback-only mode with no auth. The browser UI signs in through your IdP, sits behind an authenticating proxy, or signs in locally.</dd></dl>
<h3>What each job needs from a provider</h3>
<table><tr><th>Job</th><th>Needs a model served over</th></tr><tbody><tr><td>Embeddings (indexing, and every question)</td><td>An OpenAI-compatible <code>/embeddings</code> endpoint</td></tr><tr><td>Ask</td><td>The OpenAI Responses API or the Anthropic Messages API</td></tr><tr><td>Conversation titles</td><td>The OpenAI Responses API</td></tr><tr><td>Agent-session summaries</td><td>The Anthropic Messages API, the OpenAI Responses API or OpenAI-compatible Chat Completions, with a model that answers a forced tool call</td></tr><tr><td>Image captions, PDF extraction, thread summaries</td><td>OpenAI-compatible Chat Completions</td></tr></tbody></table>
<p>A job runs only if some provider you added speaks its protocol; there is no fallback between providers. So with only Anthropic, conversations have no titles, and embeddings need a second provider, such as a local embedding server.</p>
<h3>Replicas</h3>
<p>Every replica serves the UI, retrieval, and Ask over the API and MCP. Work that must run once per deployment runs on an elected leader, chosen by a Kubernetes Lease or a Postgres advisory lock: the Slack connection and its answers, the embedder, and every connector's sync. More replicas add a standby for that work, not capacity for it.</p>
<p>The server exposes health and readiness endpoints, and Prometheus metrics on a port of their own. During a rolling update, the old release runs against the new schema. The project does not guarantee that this works.</p>

<p>See <a href="https://diderot.dev/docs/auth/">Authentication and authorization</a> and <a href="https://diderot.dev/docs/production/#not-covered-and-known-limits">Known limits</a>.</p>
<h3>Who can read what</h3>
<p>Diderot stamps every event with one scope when it ingests it. Every search filters on the caller's scopes, in the vector query and again when the text is read from Postgres. The server computes those scopes from where the question was asked; the model never chooses them.</p>
<table><tr><th>Scope</th><th>Content</th><th>Who can read it</th></tr><tbody><tr><td><code>public</code></td><td>Anonymously readable content</td><td>Everyone</td></tr><tr><td><code>internal</code></td><td>Notion pages, Linear issues, documents from a folder of Markdown files, and agent sessions that are not owner-only</td><td>Every authenticated caller</td></tr><tr><td><code>slack-channel:&lt;id&gt;</code></td><td>Messages in one Slack channel</td><td>Anyone, for a public channel; its members, for a private one</td></tr><tr><td><code>owner:&lt;email&gt;</code></td><td>An owner-only agent session, or a one-to-one DM with the bot</td><td>Its owner</td></tr><tr><td><code>corpus:zendesk</code></td><td>Support tickets, and Help Center articles that are not public</td><td>Holders of a grant in your policy file</td></tr><tr><td><code>discord-channel:&lt;id&gt;</code></td><td>Messages in one Discord channel</td><td>Whoever you choose for that channel, every signed-in user or the groups your policy file names; asked in Discord, whoever can read the channel there</td></tr></tbody></table>
<p>Over the API and MCP, a caller gets their own set; private channels come from their Slack memberships, matched by email and cached for five minutes. An answer posted in a Slack channel is read by everyone there, so it draws only on public and internal content, public channels, and that channel's own history, whoever asked. A policy file can narrow that further for a channel.</p>
<h3>What leaves, and where to</h3>
<ul><li><b>Model providers.</b> Each Ask question, with the conversation so far and the corpus text its searches returned, private Slack messages included. A short title for each new conversation. Text to embed, unless the embedding model is local. Session transcripts, images, PDF pages and Slack threads, when you turn on summaries, captions, extraction and thread summaries.</li><li><b>The services you connect.</b> The APIs of the connectors you enable; Tavily, if you turn on web search; your Sourcebot, for code search; and the servers of your tool connections.</li><li><b>Your own infrastructure.</b> Postgres, Qdrant, your object storage and your identity provider, wherever you run them. The quickstart's one other outbound connection is the first-start download of its embedding model from Hugging Face.</li></ul>
<h3>What it does</h3>
<ul><li><b>Keeps credentials separate.</b> The API and MCP share one bearer credential. A browser credential is never accepted on either, and an API or MCP credential is never a browser session.</li><li><b>Seals pasted secrets.</b> Diderot encrypts connector secrets entered in the admin UI with AES-256-GCM under a key you hold, or reads them from environment variables.</li><li><b>Audits administrators.</b> Each state-changing action in the admin UI is recorded with the actor's email, its target and its outcome.</li><li><b>Admits Ask's MCP tools read-only.</b> An administrator ticks the tools Ask may call on each tool connection. A ticked tool attaches only if it is in a reviewed read-only set or the server marks it read-only, unless the connection explicitly allows otherwise.</li><li><b>Hides events with no scope.</b> If Diderot cannot determine an event's scope, no one can read it until it is stamped.</li></ul>
<h3>What it does not do</h3>
<ul><li><b>Mirror source permissions.</b> Access rules inside Notion and Linear are not carried over: every signed-in user can read what you index from them, and Linear's private teams are not indexed. For people asking outside Discord, Discord's roles are not copied either: you choose who may read each channel when you index it. Every signed-in user can also read an agent session unless its owner marks it owner-only.</li><li><b>Redact.</b> Neither the server nor the <code>diderot</code> client redacts a session: the client converts it and sends the whole transcript, images left out, and the server stores, summarizes, embeds and shows what arrives. Strip secrets before a session is sent, or leave a directory out with <code>diderot sessions install --exclude</code>.</li><li><b>Hide conversations from administrators.</b> An administrator can read every Ask conversation in the admin UI.</li><li><b>Terminate TLS.</b> Every listener speaks plain HTTP, and the metrics port has no authentication.</li><li><b>Rerank or match keywords.</b> Retrieval is vector-only.</li><li><b>Know who a Discord user is.</b> Discord gives a bot no email, so a question asked in Discord draws only on public content and the Discord channels its audience can read.</li><li><b>Serve more than one Slack workspace.</b></li><li><b>Match a person whose email differs</b> between your IdP and Slack. Email is the identity key.</li><li><b>Ship a Helm chart.</b> You adapt the Kubernetes example.</li><li><b>Undo a migration,</b> or delete one source's data on request.</li></ul>
<p>To report a vulnerability, email <code>security@bsky.app</code> rather than opening a public issue.</p>
<h2>Questions</h2>
<details><summary>Can I use it without Slack?</summary>Yes. Each source is turned on separately, the setup checklist needs only one, and the MCP server and HTTP API are on every install. So a deployment can index Notion, Linear, a folder of Markdown files or agent sessions and answer over MCP alone. Scheduled reports and PagerDuty investigations are delivered through Slack, and wait while it is off.</details>
<details><summary>How do agent sessions get in?</summary>The <code>diderot</code> client sends them, or an uploader of your own does. On a terminal, after sign-in, <code>diderot setup</code> checks that the server takes sessions from your account, lists the Claude Code and Codex session directories on your machine, and offers to ship them. Yes installs a background service that converts each session there and sends the whole transcript to your server, with images left out and nothing redacted. A Diderot you run for yourself needs no other collector. An uploader of your own can push session files to the HTTP endpoint instead, in the format the agent writes: Claude Code, Codex, ATIF or Hugging Face session traces. Either way the server needs session push turned on, and sessions are stored but not searchable until an administrator has chosen a model for both session-summary jobs on the Models page, one that passes each job's test. Everyone who can sign in can read a session unless its owner chooses <strong>Only me</strong> for it on their sessions page. See <a href="https://diderot.dev/docs/cli/">The <code>diderot</code> command</a> and <a href="https://diderot.dev/docs/session-ingest/">Agent-session ingest</a>.</details>
<details><summary>Does Slack need to reach my server?</summary>No. Diderot connects out to Slack over Socket Mode, so the server needs no public URL. The one inbound webhook is PagerDuty's, on a port of its own. That listener is always open, and answers 404 unless you turn PagerDuty investigations on.</details>
<details><summary>What happens to questions asked while it is down?</summary>Messages sent while Diderot is down are read when it comes back, by the sync that backs up live events. A mention is answered only if Slack delivers it again: with Slack's Delayed Events setting on, questions asked during a short outage are answered too. See <a href="https://diderot.dev/docs/slack-app/#keeping-it-running">Keeping it running</a>.</details>
<details><summary>What will it spend on model calls?</summary>Each Ask question is one model call per round of searching and reading, up to a limit you set (8 by default), plus one to write the answer. Every new or changed chunk, and every question, is one embedding input. The readiness check sends a request of a few tokens on an interval, and each is billed. The admin UI shows the tokens and cost of every conversation.</details>
<details><summary>How do I size it?</summary>Postgres holds one row per item and one chunk row for about every 1,000 characters of text. Qdrant holds one point per chunk, with the quantized vectors and the search graph in memory. The server's memory depends on load more than on the corpus: concurrent Ask turns, PDF extraction, image captions and pushed sessions. See <a href="https://diderot.dev/docs/production/#operating-it">Sizing</a>.</details>
<details><summary>How do I back it up?</summary>Back up Postgres, the key that seals pasted secrets, and the attachments bucket if you use one. Qdrant needs no backup, because it is rebuilt from Postgres, but the rebuild embeds the whole corpus again. See <a href="https://diderot.dev/docs/production/#backup-and-restore">Backup and restore</a>.</details>
<details><summary>Can I change the prompts?</summary>Yes, in the admin UI. All model instructions are one catalog. Changes collect in one draft shared by administrators and go live together as one new version with a note, and any earlier version can be made live again. When a new Diderot release ships different prompt text, a "Shipped text" tab lists what differs and you tick what to take. A conversation keeps the version it started with. Tool descriptions are the exception: they live beside the tools, in the code. See <a href="https://diderot.dev/docs/prompts/">Prompts</a>.</details>
<details><summary>How stable is it?</summary>Diderot is under active development and compatibility across versions is not guaranteed: the MCP tools, the HTTP API, schemas and settings change together. Breaking changes are called out in the release notes and in <a href="https://diderot.dev/docs/upgrading/">Upgrading</a>. Database migrations run when the server starts and cannot be undone: to go back across a release that has one, restore the backup you took before upgrading.</details>
