<p>Over a decade ago, Netlify set out to change how developers build for the web. We replaced provisioning servers and shared staging environments with a workflow where every change got its own isolated preview environment, every deploy went live atomically on a global edge network, and a bad deploy could be rolled back instantly.</p>
<p>Teams loved shipping their frontends on Netlify, but most backends still lived somewhere else, and deploying them was a very different experience. It meant wrestling with Dockerfiles and Kubernetes, applying security patches, provisioning servers and scaling them up and down. We kept getting the same question from our customers: how can the simplicity and velocity of Netlify apply to the whole stack?</p>
<p>Then, AI changed the world. We’ve welcomed millions of new builders to our platform, who want to ship ambitious, dynamic software at a pace that was unimaginable just a couple of years ago, such as real-time collaborative canvases, multiplayer apps, live chat, and agent workflows that run for long periods of time. Their complex backends kept running into the limits of what our platform could host.</p>
<p>Telling them to host part of their project somewhere else goes against our mission of empowering builders of any technical background to bring their ideas to life. So we started imagining what it would look like to bring the simplicity of the Netlify workflow and the power of our platform primitives to the rest of the stack.</p>
<p>Today we’re introducing <a href="https://docs.netlify.com/build/server/">Netlify Server</a>, a long-running server for your application’s backend. It gives your application everything a server can do, from WebSockets to in-memory state, with none of the work of running one. You build, preview and deploy it exactly like the rest of your Netlify project, and we handle the rest.</p>
<p>Netlify Server is available in Early Access today.</p>
<h2>Why a server</h2>
<p>We launched <a href="https://docs.netlify.com/build/functions/overview/">Netlify Functions</a> back in 2018 with a simple idea: you drop a JavaScript file in your project and get a backend endpoint that is built, previewed and deployed alongside your frontend, without a server to manage. We’ve kept building on these foundations, with <a href="https://docs.netlify.com/build/edge-functions/overview/">Edge Functions</a> that run snappy operations close to your visitors, <a href="https://docs.netlify.com/build/functions/background-functions/">Background Functions</a> for asynchronous work that can take several minutes, and <a href="https://docs.netlify.com/build/functions/scheduled-functions/">Scheduled Functions</a> for recurring jobs. Today, our platform handles hundreds of millions of function requests a day, powering everything from hobby projects to the websites of some of the largest companies in the world.</p>
<p>So why build a server? Because functions are built around the idea that each invocation handles one request. A function is a bit like a vending machine, where each person gets served on their own, one at a time.</p>
<p>That’s often exactly what you want, and it’s a big part of what makes functions so easy to scale and reason about. But it starts getting in the way once your backend grows past a collection of endpoints and starts to look like an application of its own:</p>
<ul> <li><strong>Waiting is expensive.</strong> A function that spends ten seconds waiting for an AI model to finish its answer, or holding a session open while a user types their next message, occupies an entire instance for those ten seconds while doing almost nothing. A hundred people chatting with your app at once usually means a hundred runtimes, each with its own cold start, its own memory and its own database connections.</li> <li><strong>Connections can’t stay open.</strong> A function responds and finishes, so it can’t hold a WebSocket open. That rules out the two-way connection that multiplayer games, collaborative editors and live chat are built on, where every participant sees what the others do as it happens.</li> <li><strong>State doesn’t stick around.</strong> Connection pools, caches and SDK clients sometimes survive from one invocation to the next, but you can’t plan around when, so every invocation has to be ready to start from scratch.</li> <li><strong>Existing servers need adapting.</strong> An Express or Hono app has to be reshaped into handlers or wrapped in an adapter before it can run as a function.</li> </ul>
<p>Serverless was designed around short, independent invocations, and these needs challenge that paradigm. And yes, we could have stretched functions to cover them, but we would end up with a confusing primitive that sits somewhere between serverless and a server without being good at either.</p>
<p>We’d rather keep functions for what they’re excellent at, and introduce a new primitive that was built from the ground up for these kinds of workloads.</p>
<h2>Meet Netlify Server</h2>
<p>With Netlify Server, we went back to first principles. Backends have had these needs for as long as the web has existed, and for decades they’ve been handled by the same thing: a server. Rather than inventing something new, we took that model and built it with everything Netlify is known and loved for. It has the same workflow, the same zero-config experience and the same platform primitives you already use for the rest of your project.</p>
<p>You write a server, and Netlify provisions it, deploys your code to it, scales it with demand and monitors it. When nothing is using it, it scales down to zero.</p>

<figure><video autoplay="" loop="" muted="" playsinline=""> <source src="https://www.netlify.com/images/blog/introducing-netlify-server/scaling-dark.mp4" type="video/mp4"/> </video></figure>
<p>Under the hood, an instance of your server is a long-lived Node.js process that handles many requests at the same time. While one request waits on a database or an AI model, the event loop serves the others, so a single instance absorbs a burst of traffic that would have meant dozens of cold starts with functions.</p>
<p>Because the process stays alive between requests, anything you set up once stays set up for as long as the instance runs. Connection pools, caches, warm SDK clients and open WebSocket connections can live in memory and be reused, instead of being recreated on every request.</p>
<p>To go back to the analogy, a server is more like a shop with staff behind the counter. It stays open, serves many people at once, and keeps things ready for the next customer.</p>
<h3>Writing a server</h3>
<p>A server is a <a href="https://docs.netlify.com/build/server/api/#entry-file">single file</a> at <code>netlify/server/index.ts</code>. You can write it as a <a href="https://docs.netlify.com/build/server/api/#handler">request handler</a>, with the same signature as a Netlify function:</p>
<figure><pre data-language="ts"><code>export default async (req: Request, context: Context) =&gt; {return Response.json({ message: `Hello from ${context.geo.city}` });</code></pre></figure>
<p>Or you can <a href="https://docs.netlify.com/build/server/get-started/#other-frameworks">bring a Node.js server</a> built with Express, Hono, or Fastify, as it is, with no wrappers or adapters:</p>
<figure><pre data-language="ts"><code>import express from "express";const app = express();const db = new Pool({ connectionString: getConnectionString() });app.get("/api/orders/:id", async (req, res) =&gt; {const { rows } = await db.query("SELECT * FROM orders WHERE id = $1", [req.params.id]);</code></pre></figure>
<p>You don’t have to configure ports, add health check endpoints or install adapters. Netlify works out how to run your server and handles the rest.</p>
<p>The same is true of all the platform primitives: <a href="https://docs.netlify.com/build/data-and-storage/netlify-database/">Netlify Database</a>, <a href="https://docs.netlify.com/build/data-and-storage/netlify-blobs/">Netlify Blobs</a>, the <a href="https://docs.netlify.com/build/ai-gateway/overview/">AI Gateway</a>, the <a href="https://docs.netlify.com/build/caching/cache-api/">Cache API</a> and others work out of the box.</p>
<p>Because it’s part of your project, it’s built and deployed with everything else. Every branch deploy and every <a href="https://docs.netlify.com/deploy/deploy-types/deploy-previews/">Deploy Preview</a> runs its own version of your backend, with its own branch of your database, so a pull request that changes your API, your schema and your UI at the same time can be reviewed in one place, on one URL.</p>
<h2>Instances you can see and control</h2>
<p>Rather than hiding server instances behind opaque abstractions, we chose to make them visible and give you a say in how they start, how they stop, and even how Netlify decides when one is too busy to take more work, while we handle the scaling itself.</p>
<figure><img alt="The Netlify Server page in the Netlify UI, showing requests, latency, memory, CPU and saturation over an hour, the number of running instances over the same period, and a table of instances with their state, start reason, age, requests, peak requests and peak memory" src="https://www.netlify.com/images/blog/introducing-netlify-server/server-page.webp"/><figcaption>The Netlify Server page in the Netlify UI, showing requests, latency, memory, CPU and saturation over an hour, the number of running instances over the same period, and a table of instances with their state, start reason, age, requests, peak requests and peak memory</figcaption></figure>
<p>We expose <a href="https://docs.netlify.com/build/server/lifecycle/">lifecycle hooks</a> for the entire lifetime of an instance. <code>onStart</code> <a href="https://docs.netlify.com/build/server/api/#onstart">runs when an instance starts</a>, before it receives any traffic, so you can warm things up. <code>onHealthCheck</code> <a href="https://docs.netlify.com/build/server/api/#onhealthcheck">runs while it’s serving</a>, and lets you report how busy your server is by its own measures, such as how deep a job queue is. And <code>onShutdown</code> <a href="https://docs.netlify.com/build/server/api/#onshutdown">runs before it stops</a>, so you can flush anything you’ve been holding in memory on the way out.</p>
<figure><pre data-language="ts"><code>import { onStart, onHealthCheck, onShutdown } from "@netlify/server";onStart(() =&gt; queue.start());onShutdown(async ({ drained }) =&gt; {export default async (req: Request) =&gt; {queue.add(await req.json());</code></pre></figure>
<p>Netlify <a href="https://docs.netlify.com/build/server/lifecycle/#instances">scales your server automatically</a>, so it keeps up with demand without running more instances than it needs. Rather than looking only at CPU usage, we read a range of signals from the JavaScript runtime and from your application to decide when an instance has room for more work and when it’s time to start another one.</p>
<p>The defaults work well for most apps, but you can also <a href="https://docs.netlify.com/build/server/lifecycle/#load-aware-routing">define your own signals</a>, such as how full a queue or a connection pool is, and we’ll take them into account when routing requests and scaling your server.</p>
<h2>What you can build</h2>
<p>Netlify Server unlocks a whole universe of use cases that were previously impossible or impractical to build on Netlify. We’ve been using it internally for a while, and it’s been truly inspiring to watch all the amazing and creative things people have built.</p>
<p>Teams across Netlify are using Server to power all sorts of workloads, and in several cases they’ve replaced entire products we used to buy with tools built in-house, with Agent Runners and other AI agents.</p>
<p>Here are a handful of examples we can talk about today. We’ll share many more over the coming weeks.</p>
<h3>Real-time collaboration</h3>
<p>A server can <a href="https://docs.netlify.com/build/server/real-time/">hold a WebSocket open</a> with every visitor in a room and push each change to the others the moment it happens. With <a href="https://docs.netlify.com/build/data-and-storage/netlify-database/">Netlify Database</a> as the shared source of truth, several instances can serve the same room without drifting apart.</p>
<p><a href="https://www.linkedin.com/in/eladrosenheim/">Elad</a> built <a href="https://netlify-server-live-rooms-example.netlify.app/">Live Rooms</a> exactly this way. It’s a collaborative board where several people move notes around the same room at once. <a href="https://dnd-virtual-tabletop.netlify.app/">Hearthlight</a>, by <a href="https://www.linkedin.com/in/youvalv/">Youval</a>, applies the same ideas to a virtual tabletop for playing Dungeons &amp; Dragons online with your friends. And <a href="https://www.linkedin.com/in/wadewegner/">Wade</a> blew our minds with <a href="https://voxel-world-game.netlify.app/">Quiver Hollow</a>, a multiplayer first-person-shooter game where you run around a small valley with a bow and try to outlast the other archers, human and AI alike.</p>
<h3>AI agents and long-running jobs</h3>
<p>A process that stays up can run an agent loop for as long as it takes, keep its working state in memory between steps, and stream progress to the page over a WebSocket while it serves other visitors. The same holds for any job that waits on a model, with the <a href="https://docs.netlify.com/build/ai-gateway/overview/">AI Gateway</a> and <a href="https://docs.netlify.com/build/data-and-storage/netlify-database/">Netlify Database</a> covering model access and storage.</p>
<p><a href="https://www.linkedin.com/in/eladrosenheim/">Elad</a> built a <a href="https://github.com/netlify-templates/netlify-server-telegram-bot">personal AI assistant</a> that you talk to on Telegram. It remembers things about you, sets reminders, watches pages for changes and searches the web. The server runs the agent loop, Netlify Database keeps its memory and schedules, and the AI Gateway provides the model, so there are no API keys to manage.</p>

<p><a href="https://netlify-server-tokyo-now.netlify.app/">Tokyo Now</a> is a mesmerizing pixel-art map of everything happening in Tokyo right now. Every five minutes the server pulls from listings, news and social posts, runs them through an AI model, and pushes every change to open pages within seconds. There’s a <a href="https://netlify-server-tokyo-now.netlify.app/how">step-by-step</a> too, and everything behind it, including the job queue and the database, runs on Netlify.</p>
<h2>Where a server fits</h2>
<p>You might be wondering whether launching a server means Netlify is walking back on composable architectures and returning to the kind of monolith we set out to untangle over a decade ago. The answer is no, absolutely not.</p>
<p>We still believe that your backend and its business logic shouldn’t dictate the web experience, that an API-first design is the right way to connect the two, and that you should use the best tool the ecosystem has for each part of the job. Netlify’s edge still serves your static assets, runs your edge functions and caches responses <a href="https://docs.netlify.com/build/server/configuration/#routing">before a request ever reaches your server</a>.</p>
<p>What changes is that your backend can now live in the same repository, build in the same pipeline and ship in the same atomic deploy as your frontend. We’re bringing the Netlify workflow to the backend, and leaving the architecture to you.</p>
<p>Netlify Server also doesn’t replace functions. A server is built to serve your app’s traffic as one process, with your routes, middleware, state, startup and shutdown in one place. Functions run discrete pieces of work that are triggered and scaled on their own, such as a webhook, a scheduled job or something that should happen when a deploy finishes. Edge functions run close to your visitors and change requests and responses on their way through.</p>
<p>For more information about when to use a server, a function or an edge function, refer to <a href="https://docs.netlify.com/build/server/#when-to-use-a-server">When to use a server</a> in the documentation.</p>
<h2>Available in Early Access today</h2>
<p>Netlify Server is available today in Early Access, on credit-based plans and on Enterprise plans with credits enabled. To build and run a server locally, you’ll need Netlify CLI 27.17.0 or later. If you build with a coding agent, run <code>netlify init</code> in your project to pull in the latest agent skills.</p>
<p>Our goal for this period is to get you building, evaluating and stress-testing real workloads, so we can gather feedback before General Availability.</p>
<p>During Early Access, a server <a href="https://docs.netlify.com/build/server/limits/#instances">scales up to 3 instances</a> (1 on Free and Personal plans), and it always <a href="https://docs.netlify.com/build/server/limits/#inactivity">scales to zero after 5 minutes without requests</a>. After Early Access, you’ll be able to keep a minimum number of instances running, so requests never wait for your server to start. The <a href="https://docs.netlify.com/build/server/limits/">limits</a> page in the documentation has the full list.</p>
<p>Netlify Server is free to use during Early Access. We want to be upfront about <a href="https://docs.netlify.com/build/server/#pricing">how pricing will work</a> when it reaches General Availability, though. Usage will be billed based on two meters: reserved memory (in GB of RAM per hour) and active CPU time (in vCPU hours), at rates we’ll announce before GA. We might still adjust these meters as we learn from Early Access.</p>
<p>Other metered features in your project, such as bandwidth and web requests, are <a href="https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/">billed as they are today</a>. You can <a href="https://docs.netlify.com/build/server/logs/">track your usage in the Netlify dashboard</a>, and before GA we’ll reach out to anyone whose usage suggests they’d need a bigger plan or more credits to keep going at the same pace, so you won’t be caught off guard.</p>

It’s a foundation we’re excited about, and we’re hard at work building on it to unlock new capabilities on Netlify, with the goal of powering the next generation of applications and the new generation of builders creating them.
