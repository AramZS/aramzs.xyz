<html><body><h4>By optimizing our biggest Node.js service, we cut our compute costs by 38<strong>%</strong></h4><figure><img alt="A person is skating near the mountains." height="1365" src="https://miro.medium.com/v2/resize:fit:1400/0*QB6D4e1uZe8W7tDq" width="2048"/></figure><p>By optimizing our biggest Node.js service, we cut our compute costs by <strong>38%: </strong>we ran <strong>30%</strong> fewer pods, reduced memory usage by <strong>20%</strong> per remaining pod, and took up to <strong>10%</strong> off latency at p75, p99, and p99. No new hardware, and no code changes in the service itself. The gains came from changes to our Node.js platform and a fresh look at configuration choices we had left untouched for years.</p><h3>How a Booking.com page is put together</h3><p>Booking.com helps people find places to stay, book flights, taxis and rental cars, and find things to do when they get there. In 2025, 1.2 billion room nights were booked across Booking Holdings (<a href="https://www.bookingholdings.com/about/factsheet/">fact sheet</a>).</p><p>Our back-end is a mix of Java, Perl, Rust and Node.js. Node handles server-side rendering, some data APIs, and much of our tooling. This post focuses on Node and the rendering side.</p><p>We server-render pages heavily for two reasons. Pages have to work when client-side JavaScript is not available, and they have to be crawl-able. React SSR is CPU-bound: a render occupies one thread doing CPU-heavy work rather than just waiting on I/O, so throughput is bounded by how many cores the service can keep busy.</p><p>Each major page has its own Node rendering service, owned by the team responsible for that page: the home page, the search results page, the property page and so on. The page itself is assembled from sections owned by different teams. For example, on the property page those include the header, the photo gallery, the reviews, the rooms table and others.</p><figure><img height="1068" src="https://miro.medium.com/v2/resize:fit:1400/0*dCJsYsEaWqFlgOBQ" width="1799"/></figure><p>That structure came out of how we moved off Perl. Rather than rewriting a page in one go, we replaced it one fragment at a time: a Perl-rendered page would start serving a single React component from a Node service, then another, with each swap behind an experiment so it could be measured and reverted on its own. Rewriting a whole page at once would have been a single change too large to evaluate or safely undo.</p><p>Some of those components are not bundled into the rendering service at build time. Instead, they are loaded at runtime through Webpack Module Federation (and native ES modules), so a team owning a component can deploy an update and every page using it picks up the new version without anyone redeploying a rendering service. Each rendering service declares its dependencies and regularly fetches updated <code>.css</code>, <code>.js</code> and <code>.json</code> static files published by component owners, which hold the new version of the required component.</p><blockquote><p>Practical example: the team owning the header and footer can publish a new version of their components, and it will be distributed across all Node.js rendering services within minutes, without a full deployment for each page.</p></blockquote><p>A rendering service handles two kinds of requests with very different costs:</p><ul><li>Full-page renders, 100 to 400ms, dominated by long CPU-blocking tasks. We’re using React’s <code>renderToString</code>, so a component render is one big blocking call.</li><li>Calls to the <code>/metadata</code> endpoint, usually under 30–50ms. We actively apply code splitting, so this endpoint serves components that render client-side only, lazy-loaded ones, and acts as a fallback when server-side rendering fails. It returns what a component needs on the client: its copy tags for the current locale and its experimentation parameters or other required metadata.</li></ul><p>In front of the rendering services sit a gateway and a routing service that maps a URL to the service that owns it. Every pod also runs sidecars that are standard across the company regardless of language: a service mesh proxy, an experimentation sidecar, and nginx, which handles ingress traffic and shared metrics.</p><pre><code>GET /some-page (Initial page rendering, React SSR)
      │
      ▼
 ┌─────────┐     ┌──────────┐
 │ gateway │────▶│ routing  │
 └─────────┘     └──────────┘
                      │
                      ▼
 ┌────────────────────────────────────────────┐
 │  rendering service pod                     │
 │  sidecars: mesh, nginx, experimentation    │
 │  ┌──────────────────────────────────────┐  │
 │  │ process manager                      │  │
 │  │    worker-1  worker-2  worker-3  …   │  │
 │  └──────────────────────────────────────┘  │
 └────────────────────────────────────────────┘
                      ▲
                      │ JS, CSS and JSON metadata, fetched at runtime
       ┌───────────┬──┴────────────┐
   ┌───┴────┐  ┌───┴────┐  ┌────────┴────────┐
   │ header │  │ footer │  │ other-component │
   └────────┘  └────────┘  └─────────────────┘
      component services, owned by other teams</code></pre><pre><code>browser (Client side rendering fragments)
   │
   │ 1. static JS and CSS chunks
   ├──────────────────────────────────────────▶ CDN
   │
   │ 2. /metadata for client-only and lazy components (translations, experimentation)
   └──▶ gateway ──▶ route ──▶ rendering service</code></pre><h4>The defaults we set before</h4><p>Node runs JavaScript on one thread, so a single process per pod leaves most of the available cores idle and gives you one point of failure. A process manager solves both, and it lets several workers share the sidecars in the pod rather than each needing a set of their own. We used <a href="https://github.com/Unitech/pm2">pm2</a>, which builds on Node’s <a href="https://nodejs.org/api/cluster.html">cluster</a> module and was the established choice at the time.</p><p>We settled on four to eight workers per app (decided by service owners), leaving some headroom for growth and changes.</p><p>That setup ran for years without complaint, which is part of why nobody revisited it. Nothing in it triggered an alert or investigation. Meanwhile two things changed underneath it: the Node.js platform absorbed a lot of functionality as we migrated features and components off the legacy Perl app. And rendering more and more shifted from fragments to whole pages, which changed the size and duration of a typical request.</p><p>When we finally looked at the whole setup rather than one service at a time, we found several opportunities to improve it.</p><h3>What we were optimizing for</h3><p>Performance here means two things. The first is what a <em>user experiences</em>: how long the page takes to arrive. For server-rendered pages that is mostly how long the render itself takes, plus the time the request spent waiting for a worker. Averages are not much help. A p99 render belongs to a real person, so the spread matters as much as the middle, and both GC pauses and time spent queued behind someone else’s page render land in it.</p><p>The second is <em>efficiency</em>: how much CPU and memory it takes to serve a given rate of traffic, which decides how many pods we run and what the service costs.</p><p>These goals can compete, and you can sometimes buy latency with more compute by running more pods with less work in each. We wanted to improve efficiency without compromising user-perceived performance, and ideally improve that too.</p><p>There was a second requirement, unrelated to performance: product teams should not have to do anything. We own the framework these rendering services are built on, and there are more than 70 of them.</p><p>So the target was a change teams could take by flipping a flag, with a documented way back if it went wrong.</p><h3>From processes to worker threads: from pm2 to wattpm</h3><p>pm2 uses Node’s <code>cluster</code> module. Each worker is a separate OS process, and a supervisor process accepts connections and hands them out. It costs an extra hop on every request, and a full duplicate of everything V8 builds at startup.</p><p>In comparison, <a href="https://github.com/platformatic/platformatic">wattpm</a> runs workers as worker threads and lets the kernel distribute incoming connections using <code>SO_REUSEPORT</code> instead of routing them through a supervisor process. Overall it promises less overhead and modern Node runtime features, so we decided to give it a try, hoping for better performance and more efficient resource utilization.</p><p>We started with isolated performance tests. They were inexpensive to run, and a negative result would have ended the project. We tested the app on Linux using Docker and k6. Under light load, the two setups performed similarly.</p><p>The differences emerged under load. We measured how much traffic each setup could handle without errors, rejected requests, or breaches of our latency SLO (be it median latency, p75 or p99.95).</p><p>We tested three high-pressure scenarios:</p><ul><li>A powerful pod with 4 CPU cores bombarded with component render requests. We saw that the <code>wattpm</code> version consistently handled 20 to 40% more requests within our latency SLO threshold than pm2.</li><li>A pod with less compute (2 cores) and more pressure, by artificially making the React rendering process even more blocking, up to 200ms. The two setups hit the same throughput ceiling, but latency was better with <code>wattpm</code>, by 5 to 30% at p75 and p90. We don’t expect to ever face this scenario in production, it was interesting to check the limits.</li><li>A mixed workload, with heavy renders and light requests interleaved the way real traffic arrives. This is the most realistic scenario. The <code>wattpm</code> installation handled 40 to 50% more requests on average between test runs, and the version using fewer than the default 6 workers won.</li></ul><p>Here are some of the interesting runs in that test suite:</p><figure><img height="1056" src="https://miro.medium.com/v2/resize:fit:1400/1*mQ5NUI1x1O0ml1MzWJ2Ynw.png" width="1781"/><figcaption><em>Number of parallel k6 workers each setup could handle. Higher is better. The graph aggregates results across multiple runs. In all cases, the containers had 4 CPU cores and plenty of memory.</em></figcaption></figure><p>For moderately heavy workloads, that pattern was consistent: similar/same latency, more throughput.</p><p>We saw a different picture with less compute and same or more pressure:</p><figure><img height="880" src="https://miro.medium.com/v2/resize:fit:1400/0*tON8fInWEUk4nc-7" width="1418"/><figcaption><em>Extreme stress scenario: heavy load but only 2 CPU cores. Throughput is equal. Configurations with six or more workers failed early and were excluded from the tests.</em></figcaption></figure><p>However, the latency was not:</p><figure><img height="1002" src="https://miro.medium.com/v2/resize:fit:1400/1*sOXaa7k7CGNzIe3XtkLUew.png" width="1627"/><figcaption><em>Synthetic test with mocked dependencies, does not represent the real latency; <code>wattpm</code> 2 workers was the clear winner with the most stable latency and good capacity.</em></figcaption></figure><p>In all these scenarios and test runs, the only difference was the move from pm2 to <code>wattpm</code>. V8 settings, GC settings and the app itself remained the same (we iterated on those too, later in this article).</p><p><code>wattpm</code> setup was also faster, because cluster balances in user space by passing every connection from the primary to a worker over IPC, while <code>SO_REUSEPORT</code> lets each worker accept straight from the kernel with no coordination in the request path.</p><h3>Proving it in production</h3><p>The synthetic results justified a production test. It is still important to keep in mind that synthetic tests do not always translate to production wins, and often deliver unexpected or very different outcomes. We needed to conduct a test on real production traffic, ideally as a scientific A/B test.</p><p>The idea behind most A/B tests is simple: you split your users into two (usually equal) cohorts, one is served the v0 (default) version while the second is served v1 (the changed version). Metrics are collected together with a record of which version was shown to each user, and then compared with proper statistical tests. This pseudo-code sample demonstrates how they are usually implemented using Booking in-house libraries:</p><pre><code>import {ButtonOld, ButtonNew} from 'component/button';

// trackExperiment does a coinflip, records it and returns the result
const Button = trackExperiment('try_new_button') ? ButtonNew : ButtonOld;
return &lt;Button /&gt;;</code></pre><p>This works great for product changes, but what if the test requires more than a simple runtime “if” check? With the <code>wattpm</code> migration, we change the application startup logic itself and replace <code>PID 1</code> of the application container, so that it cannot be switched for each request individually.</p><p>Instead of just doing a coinflip in Node.js, we ran two complete installations of the same application side by side, with the same pod count and the same resources, and split traffic between them at the routing layer one level above:</p><pre><code>                                          ┌──────────────────────────────────────┐
                                    50%   │  install A: cluster / pm2             │
┌─────────┐     ┌──────────────┐ ───────▶ └──────────────────────────────────────┘
│ Gateway │────▶│   Routing    │
└─────────┘     │  (coinflip)  │          ┌──────────────────────────────────────┐
                └──────────────┘ ───────▶ │  install B: worker threads / wattpm   │
                                    50%   └──────────────────────────────────────┘</code></pre><p>This approach required much more preparatory investment: deployment pipelines had to update both installations simultaneously, keep them on the same version in case of a revert, keep the resource settings and pod count equal, and so on. It was worth it: we were able to isolate the <code>wattpm</code> / <code>pm2</code> change, and also use this setup for further tests later, not limited to process management.</p><p>Once we got it right, the next steps were simple:</p><ul><li>Compare both installations under equal and normal conditions</li><li>Add more pressure by removing some of the pods, and see how far we could go</li></ul><p>The main hypothesis we defined was that with the <code>wattpm</code> installation, we could maintain or improve our latency while requiring far fewer resources or total pods to serve the traffic.</p><h4>First disparity and the load balancing insight</h4><p>Production revealed an unexpected pattern. Under light load, <code>wattpm</code> matched or slightly improved on pm2’s latency. Under moderate load, it fell behind. Under heavier load, it pulled ahead again. The moderate-load result contradicted our synthetic tests. What was different in production?</p><p>Nothing in aggregated metrics explained it. Aggregated event loop lag and GC metrics were normal on both sides, CPU usage was normal, and heap settings were identical. Local profiling showed nothing and we could not reproduce it outside production.</p><p>We had no per-worker visibility at the time, which is the reason it stayed hidden. Everything we were looking at was aggregated across the pod (as p50/p75/p90), and an aggregate of six workers hides an imbalance between them. So we picked a pod under load and inspected it directly: container throttling, allocator statistics, per-core CPU, and finally CPU ticks broken down per process for pm2 and per thread for the new setup.</p><h4>Fixing load balancing</h4><p>Both setups were uneven. With pm2 the busiest and least busy workers differed by 10 to 20%. With worker threads and kernel distribution the spread reached 20 to 40%.</p><p>The cause was two defaults meeting each other. nginx talks to the app over loopback, and <code>tcp_tw_reuse</code> is set to <code>2</code> by the kernel, which lets it recycle those loopback connections quickly. <code>SO_REUSEPORT</code> picks a worker by hashing the connection’s source and destination address and port. With the source ports being recycled, the hash kept landing on the same destination, so the work was unevenly distributed.</p><p>The most straightforward idea would have been to skip <code>nginx</code> completely, but it was still needed for uniform metric collection and reporting. Instead, we decided to use it to our advantage: <code>nginx</code> has <a href="https://nginx.org/en/docs/http/load_balancing.html">built-in</a> load-balancing capabilities, so we used them to fix the connection reuse problem and later to experiment with going beyond the standard approach of round robin across 6 equal workers.</p><p>We changed the way the <code>wattpm</code> installation started. Instead of 6 workers listening on <code>:3000</code>, each worker listened on the next port in sequence: <code>:3000</code> for the first, <code>:3001</code> for the second and so on.</p><p>Then in <code>nginx</code> we could just do this (round robin is the default):</p><pre><code>upstream http_backend {
  server 127.0.0.1:3000;
  server 127.0.0.1:3001;
  server 127.0.0.1:3002;
  server 127.0.0.1:3003;
  server 127.0.0.1:3004;
}</code></pre><p>And it worked great: the performance disparity completely faded and <code>wattpm</code> was outperforming the <code>pm2</code> installation in all types of load and situations. However, given the big variety of services we have, with both light and heavy requests, could we go further and make it more efficient?</p><h4>Going beyond simple round robin</h4><p>Here, we had two main hypotheses to check:</p><ul><li>Given that we have very heavy (page / component server-side rendering) and lightweight (<code>/metadata</code>) endpoints, can we achieve better load balancing by splitting them?</li><li>Would a load-balancing algorithm other than round robin demonstrate better results?</li></ul><p>With those in mind, we ran our isolated test suite again (this time with <code>nginx</code> added). We tested the old <code>pm2</code> setup, <code>wattpm</code> alone, and different combinations of <code>wattpm + nginx</code> configuration, as a sort of matrix comparison.</p><p>This is what one possible <code>nginx</code> config looked like:</p><pre><code>upstream http_backend_heavy {
  least_conn; # changing from default round robin

  server 127.0.0.1:3000;
  server 127.0.0.1:3001;
  server 127.0.0.1:3002;
  server 127.0.0.1:3003;
}

upstream http_backend_light {
  server 127.0.0.1:3004;
}

server {
  listen 8080;

  # lightweight endpoints get their own worker
  location ~ ^/api/(metadata|events) {
    proxy_pass http://http_backend_light;
  }

  # everything else is a render
  location / {
    proxy_pass http://http_backend_heavy;
  }
}</code></pre><p>We saw that moving light requests to a dedicated worker gave better tail latency (p99.9) and throughput at lower memory use. We also noticed that the sweet spot was 4 page rendering workers plus 1 auxiliary worker for light requests, on pods requesting 2.5 CPU cores. Fewer workers increased latency; more workers used additional memory without improving throughput.</p><p>As for load balancing, round robin did quite well. Only in the 4+1 scenario did <code>least_conn</code> demonstrate marginally better results in latency, 2 to 3% at p90 and up to 7% at p99.9. The effect likely relates to our pages being highly personalized, with different workload weight between the mobile and desktop versions of the page — and we tried to reproduce that in our local tests, by varying request parameters and components to render.</p><p>We decided to continue with the 4+1 worker split, which brought the biggest benefit, and <code>least_conn</code> as a small bonus for this specific service.</p><h3>Spending the headroom</h3><p>By this point two changes had freed memory.</p><p>Firstly, our move to <code>wattpm</code> (and hence worker threads) reduced the overall memory footprint, even though each worker still has its own V8 isolate.</p><p>Secondly, we found that with <code>wattpm</code> and <code>nginx</code> load balancing, we only needed 4 page rendering workers and 1 auxiliary worker instead of 6 fully loaded ones, which also reduced our memory usage. We spent some of that headroom on garbage collection.</p><p>Two key parameters for tuning V8 garbage collection in Node.js are:</p><ul><li><a href="https://nodejs.org/api/cli.html#--max-old-space-sizesize-in-mib">max-old-space-size</a></li><li><a href="https://nodejs.org/api/cli.html#--max-semi-space-sizesize-in-mib">max-semi-space-size</a></li></ul><p>You can read more about them in the Node.js documentation, starting from this <a href="https://nodejs.org/learn/diagnostics/memory/understanding-and-tuning-memory#understanding-and-tuning-memory">article</a>. What is important here is that max old space size was already widely adopted in our Node services and mostly well defined, based on each service owner’s specific needs, so we did not need to change anything there.</p><p>However, customizing semi space size was not widespread at all, and most of the services were using the old <code>16MiB</code> limit set by the framework. We decided to revisit this default and provide better recommendations, especially since we freed around 30% of RAM.</p><p>The old <code>16MiB</code> limit suited fragment rendering, but it is too small for full pages. We gradually raised it from <code>16MiB</code> to <code>32MiB</code> and then to <code>64MiB</code> in the service. Scavenges became proportionally less frequent, our p75, p99 and p99.9 improved, and together with the previous improvements this allowed us to reach the 10% latency gain at p75 and p99.9 mentioned above. Increasing the memory beyond <code>64MiB</code> yielded only a minor benefit while using significantly more memory, so we stopped there.</p><p>The cost is memory: total young generation per worker runs up to roughly three times the semi-space size, because there are two semi-spaces plus a separate space for large objects. Thanks to the earlier memory savings, our pods were still using less memory than before.</p><figure><img height="280" src="https://miro.medium.com/v2/resize:fit:1400/0*yh-QliWH7DfWhF10" width="859"/><figcaption><em>Latency win: green installation (tuned <code>wattpm</code>) has consistently better latency, up to <strong>10%</strong> improvement</em></figcaption></figure><h3>Module reloading</h3><p>The last change was ours, and it was in code rather than configuration.</p><p>When a component team deploys, every rendering service using that component picks up new remote entries while it is running. Under pm2 the new metadata had to be pushed to each worker process separately, and each push allocated somewhere between 50 and 150MiB for a large service. They could not be done in parallel without the coordinating process running out of the memory available in the pod, and doing them in quick succession caused a CPU spike and a dip in availability, so we staggered them with deliberate sleeps.</p><p>Most of the old version was garbage collected afterwards. Not all of it: some ESM module registration state survives, and V8 does not clean it up, so a little memory accumulated with every ESM dependency deployment. On a service running through a busy release period, that adds up.</p><p><code>wattpm</code> let us replace the worker instead of updating it in place. Workers rotate one at a time: a new worker starts and reads the new metadata, the old one drains its in-flight requests and exits, which releases everything it was holding including the leftover module state. Because of <code>SO_REUSEPORT</code>, restarting a worker is inexpensive and transparent to callers, even with one worker per port.</p><figure><img height="428" src="https://miro.medium.com/v2/resize:fit:1400/0*gm0VCYBje1vqI8D6" width="894"/><figcaption><em>We first tested this approach on a less critical service that was experiencing problems with ESM runtime updates. Restarting workers gradually during module updates resolved those problems.</em></figcaption></figure><h3>Putting all things together</h3><p>By that point, we were confident that all these changes had a positive impact on the performance and resource usage of our app, and that it was time to roll it out. Capturing latency wins is easy: with a perfect 50/50 traffic split, we can see each percentile side by side and confirm that yes, the new version has better latency and fewer tail spikes. That is already a win.</p><p>But how to estimate the capacity gains?</p><p>Firstly, we decided to conduct a set of production tests with individual pods. Taking 2 random pods, one with <code>wattpm</code> and one with <code>pm2</code>, we gradually and simultaneously increased the traffic ratio for each, using service mesh settings. While we did this, we monitored:</p><ul><li>Total pod RPS (to ensure that the test is valid)</li><li>pod resources (CPU, memory) in all containers</li><li>Node.js metrics: event loop utilization, event loop lag, GC time and count, heap size</li><li>Latency and status codes as seen from outside</li></ul><p>We repeatedly increased the traffic load, conducting tests in different clusters. We defined the throughput ceiling as the maximum value while all the aforementioned indicators were within normal limits and there was a 15% headroom before reaching the breaking point.</p><figure><img height="516" src="https://miro.medium.com/v2/resize:fit:1400/0*FNKv5HaRbonW-sEL" width="1777"/></figure><p>Across all test runs, wattpm pods handled at least 30% more traffic than pm2 pods, with the same number of CPU cores and lower memory requests</p><figure><img height="312" src="https://miro.medium.com/v2/resize:fit:1400/0*e4cJR34JqNha0r4s" width="2048"/><figcaption><em>One of the metrics we monitored during such tests — CPU usage. Equal traffic, equal work. The yellow line represents a wattpm pod.</em></figcaption></figure><p>After that, we were able to estimate the new desired pod count. The last part of the rollout was simple: every day, we reduced pod count in <code>wattpm</code> by 5% (from the base value) and monitored the system state until we reached 30% pod count reduction. It was possible to go even further, but we preferred to leave extra headroom and later look at capacity and scaling with auto-scaling tools.</p><h3>Results and going back to the community</h3><p>Once we confirmed that everything worked as expected and the new setup was fully stable, we shared a one-pager with our framework and Node communities. We shared 3 key wins from this project:</p><ul><li><strong>30%</strong> fewer pods needed for the biggest Node service in the company</li><li>The remaining pods required <strong>20% </strong>less memory</li><li>Tail latency improved, together with better resilience under load</li></ul><p>Adopting it is simple: add <code>PM_CHOICE=wattpm</code> to your Kubernetes config and go through a short guide on how to right-size your Node.js app resources and configuration (or hand that to your AI agent). Now every product team can benefit from improved latency, capacity and resilience for a fraction of the cost.</p><h3>Possible follow ups</h3><p>There is probably more to get from Node.js here. <code>SO_REUSEPORT</code> also permits custom load balancers, and <code>eBPF</code> makes some approaches practical that were not tried before, allowing even lower overhead.</p><p>The runtime metrics that <code>wattpm</code> exposes cheaply also open up auto-scaling on signals that reflect what a Node process is actually doing rather than CPU alone: horizontally, by scaling pods on Node-level metrics, and vertically, by auto-adjusting how many workers run inside a pod.</p><p>Still, it is better to move one step at a time, and we hope to share further wins with the community later.</p></body></html>
