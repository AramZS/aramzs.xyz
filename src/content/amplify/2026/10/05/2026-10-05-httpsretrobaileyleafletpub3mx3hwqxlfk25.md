<p>2026 has been the year that LLM development has boomed, and with it more software than we had the year before, with some of it being developers building things they wanted, but never could quite spare a couple of weeks to build out. This will not be a post about LLMs besides this introduction section and some stray thoughts, but every project listed here was built with the assistance of a ghost in the machine.</p>
<p>Like a majority of developers in our field, I started exploring LLM development this yearore through prompting than via an IDE/editor. As developers, our jobs are a continuing education field. Learning new tools and keeping up with changing standards to fulfill the obligations of our profession. Personally, I usually do this through personal software or Open Source code/projects. Not everything I release makes me $$$, but it is training and a way to learn new things that in turn get used in my professional job.</p>
<p>There are a couple of reasons I like doing personal or throwaway projects when learning a new tool, LLMs in this case.</p>
<ol start="1"><li><p data-index="4.0">The first thing you build with it is usually shit. You don't know the tool, so you usually end up doing something wrong, or maybe not the best. Let's you learn the hard lessons without inflicting that on others or in a setting where you are paid for this labour </p></li><li><p data-index="4.1">Building software for others, you usually put yourself in the users of that softwares shoes, or get requirements from others. Personal software you're the user who wants it so it helps to know exactly what you want and how it should work as you're building it out. So you don't have to figure out the tool and parse what someone wants you to build.</p></li></ol>
<p>A note about the quality of the software. A lot of these projects were written entirely by an LLM. I try to be very careful about what I post publicly about what I work on and what I plan on continuing to support in the future. These are almost all personal projects for myself or others. Almost all if not all, were written completely by an LLM to explore what its strengths and weaknesses are as a tool to write software. I am still trying to come to grips with the world we live in that has the ability to create unlimited projects, and what that looks like. What do I share with people? What do I support if I do share with people? And the million other questions we are asking ourselves about LLMs. You may find some of these useful, or completely broken. But this is a showcase of what I've been building over the year and not sharing online.</p>
<h2 data-index="8"><a href="https://retrobailey.leaflet.pub/3mx3hwqxlfk25/#claudebar">ClaudeBar</a></h2>
<p>The first one up is a little macOS Swift menubar app to show my Claude usage. Reads your Claude API token from your Mac's keychain store. Does not show anything in great detail, or even support the Fable usage bar, but it was my first test of directing an LLM to read a source repo (<a href="https://github.com/grzegorz-raczek-unit8/claude-quota">original idea I saw in python</a>) to a new language. I was wanting it as a native MacOS in swift. Can see the source on the <a href="https://tangled.org/pds.dad/claudebar">tangled repo</a>.</p>

<p>Lots of amazing wikis on <a href="https://www.fandom.com/">fandom.com</a>, along with lots of ads. I can't fault anyone for getting the paycheck, but the ads were to the point that I cannot use it sometimes. <p>Fandom's are powered by <a href="https://www.mediawiki.org/wiki/MediaWiki">mediawiki.org</a>, which each one exposes an API you can hit. So I thought I would try to write my own client to those APIs. it's not very good, and I think it's a great example of "LLMs can build a lot, but unless you put in the time to be specific and work with the project it's not going to be good." Can be seen in the pictures below comparing my client vs the actual wiki with all the care and love those editors put into making those pages.</p>
<p>Verdict of this? Can tell that even using all the new frontend tools, caching, etc fandom's frontend was still much more usable and with mine being a pale imitation, even with all the ads on fandom's. And that's an important lesson to learn with these tools, even with all the power they give developers, you are not going to be writing great software right off the bat and replacing years of care and work in a day to make a better product. <p><a href="https://github.com/oxygencobalt/Auxio">Auxio</a> is a fantastic music player. Ever since I moved to Android over a month ago, it's what I use to listen to music. But with it, I missed having what I listen to track with <a href="https://teal.fm">teal.fm</a>.</p>
<p>This fork adds 2 features</p>
<ul><li><p data-index="43.0">Tracks what you listen to teal.fm. Uses App Passwords so I don't have to re-login every 2 weeks with a public oauth client or run a web server to proxy those writes </p></li><li><p data-index="43.1">Can sync/download your music library from a webdav share. I have a Synology NAS and wanted an easy way to sync what I buy from Bandcamp instead of download, put in a zip, download again on my phone and move it to the folder. </p></li></ul>
<p>Neither of these features feel in line with the goal of Auxio as a simple offline music player, so I have not reached out to see about having them merged, and I feel like doing so would put an extended strain on an open source maintainer. Especially as these commits/features were generated by an LLM. I have made a small sponsorship as thanks for such great software and a base for me as a developer to be able to add features onto. Can see the source on <a href="https://tangled.org/pds.dad/auxio-teal-fork">tangled</a></p>
<h2 data-index="46"><a href="https://retrobailey.leaflet.pub/3mx3hwqxlfk25/#cyddcheap-yellow-display-dashboard">CYDD(Cheap Yellow Display Dashboard)</a></h2>
<p>The CYD is a cheap yellow display powered by an ESP32, a great cheap device to start writing some embedded code on. More info on it <a href="https://github.com/witnessmenow/ESP32-Cheap-Yellow-Display">here</a>. I bought mine a year ago for $19, and it has sat on my desk ever since. Before I got nerd sniped by atproto I was very into rust embedded development (See <a href="https://retrobailey.leaflet.pub/3mnnskzjn6k2c">Rust 🦀 on the RP2040</a>, <a href="https://retrobailey.leaflet.pub/3mnnti2hpkk2u">Running a HTTP server on the Pico W with Rust 🦀</a>, <a href="https://retrobailey.leaflet.pub/3mnpv64zct22z">Getting started with Rust 🦀 on the 10¢ microcontroller</a>, and more on this blog), but all of that was written by hand without LLMs.</p>
<p>Learning embedded development and writing code that close to the machine is the most fun I have had in my development career and some of the most rewarding. It was a lot of taking things that did something one way, and doing it in another with a new language, a new device, and usually different hardware. A never ending series of challenges, and usually was all personal projects so could make them as polished or as bad as you'd want!</p>
<p>I was a bit nervous to see something I had so recently spent weeks on learning to perfect and write code just for a single device distilled into a series of English requests to add the features in an afternoon. Well, it did it. It wrote what seems to be a pretty solid rust firmware for the CYD. Even did some crafty parsing of JSON requests to cut down on memory. Still thinking about how I feel about it, but the CYD in it's 3D printed case sits on my desk and I use it daily.</p>

<h2 data-index="55"><a href="https://retrobailey.leaflet.pub/3mx3hwqxlfk25/#what-have-i-learned">What have I learned?</a></h2>
<p>I learned a lot about how to use these tools while writing these projects. What worked well and what didn't. I think the main takeaway is: if you care it shows, if you don't, it does not show. It is also still important to know what you want built, what tooling to use, what frameworks, what UI components, what APIs, etc. Knowing this and directing the LLM has always led to software that I wanted and performed more along the lines I expected.</p>
<p>A lot of these projects are very simple, or full of bugs and the original version, if there is one, is superior in every which way thanks to the love and care that went into those projects. I think you can use these tools to make the process of creating software faster, but I still think leaving a human in the loop is the only way to make software great.</p>
<p>I think most developers, when they release a project, know it's not done. There's a bug they can't quite figure out, there's a feature they missed, or any of the 100 things. Telling an LLM "do a breakthrough" is not a silver bullet to do all of those things, but I do think using an LLM does give the developer the capacity to do that where they may of not been able to before with a smaller investment in time and effort.</p>
<p>All of these projects showed me that in one way or another, and I ended up with some stuff I use almost daily now.</p>
<p>I may write another proper LLM post one day and explore these concepts in more detail and how I feel about them, like I did in <a href="https://retrobailey.leaflet.pub/3mmsk37ojg22k">The LLM post</a>. I may write one that talks more so how I use these tools when I build software for others. Let me know what y'all think about that? But anyhow, thanks for reading and checking out my slop gallery of learning.</p>
