title: In Which A Book Lexicon is Born
---
<p>First off, huge credit to <a href="https://discourse.atmosphere.community/u/omg.jacky.wtf">@omg.jacky.wtf</a> for actually getting this moving.</p>
<p>A bunch of us have been talking about books, bibliographic data and shared lexicons for a while, but mostly with our heads down building our own projects. Jacky got people into a room and started turning that into something concrete. That’s important.</p>
<p>I think the next step is getting the builders together and treating this a little like what happened with <a href="https://standard.site/">Standard.site</a>.</p>
<p>We already have working code and different approaches in the wild. <a href="https://github.com/olamaelcu/bibliograph">Bibliograph</a> is now doing some really interesting work on the bibliographic side. BookHive, @xardex.dev, has a working book and reader implementation (CAVU is working on a reader - <a href="https://discourse.atmosphere.community/u/chris.pardy.family">@chris.pardy.family</a>). Byline.pub, me, has been working on author and book records. There are other projects coming at this from reading, publishing, metadata and discovery as well.</p>
<p>None of that work should be thrown away. Quite the opposite. That’s the material we should be bringing to the table.</p>
<p>I also don’t think we should assume any existing <code>book.*</code>, <code>*.book</code> or project namespace automatically becomes <em>the</em> canonical book lexicon. We aren’t really at that point yet. The useful question is: <strong>what is common between the things we’re already building, and what should apps across the ATmosphere be able to rely on?</strong></p>
<p>I’d suggest we establish a small Book/Bibliography Lexicon working group.</p>
<p>Not an IETF bureaucracy. Nobody needs another committee eating their evenings.</p>
<p>A group of the people actually building this stuff.</p>
<ul> <li> <p>gather the existing schemas and implementations</p> </li> <li> <p>identify the common primitives: works, editions, identifiers, contributors, authorship, reading state, reviews, relationships, etc.</p> </li> <li> <p>run a few workshops across different time zones</p> </li> <li> <p>document the places where our implementations disagree</p> </li> <li> <p>get something resembling a v0 proposal</p> </li> <li> <p>put it out publicly for comment</p> </li> <li> <p>implement it in several real applications</p> </li> <li> <p>learn where it’s wrong</p> </li> <li> <p>then publish the shared lexicon</p> </li> </ul>
<p>Basically: rough consensus <strong>and running code</strong>.</p>
<p>I’d also really like to invite some of the folks involved with @standard.site into that discussion — <a href="https://discourse.atmosphere.community/u/aka.dad">@aka.dad</a>, <a href="https://discourse.atmosphere.community/u/brookie.blog">@brookie.blog</a>, <a href="https://discourse.atmosphere.community/u/awarm.space">@awarm.space</a> and anyone else I’ve missed. They’ve already gone through the exercise of getting several independent AT Protocol applications to converge on common lexicons, and there are probably lessons there that would save us some bruises.</p>
<p>Jacky’s thread is a damn good starting point. Bibliograph gives us something concrete to experiment against. The various book apps give us real-world requirements.</p>
<p>Now we need to get those people around the same virtual table.</p>
<p>Different projects. Different time zones. Different needs. But we all have a stake in getting this right.</p>
<p>I’d be very happy to help organise it.</p>
